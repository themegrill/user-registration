# Membership and payments

Read from `modules/membership/` (`includes/Admin/Database/Database.php`, `Admin/Services/*`, `AJAX.php`, `Admin.php`, `Crons.php`), `includes/Functions/CoreFunctions.php`, `modules/functions-ur-modules.php`. Membership is on only when `ur_check_module_activation( 'membership' )`.

## Data model
- **Plans** are posts of type `ur_membership`. The plan configuration is **JSON in `post_content`** (keys seen in code: `type` = `free|paid|subscription`, `status`, `amount`, `payment_gateways[<gateway>]['status']` = `on|off`), plus post meta `ur_membership`, `ur_membership_description`, `_urm_paypal_product_id`. **Groups** are `ur_membership_groups` (meta `urmg_mode`, `urmg_memberships`). **Teams** are `ur_membership_team` posts (meta `urm_team_data`, `urm_team_seats`, `urm_used_seats`, `urm_team_leader_id`, `urm_member_ids`, `urm_member_emails`, `urm_order_id`, `urm_subscription_id`, `urm_tier_info`), created only when the `team` module is on.
- **Tables** (names from `TableList`, all prefixed with `$wpdb->prefix`):
  - `ur_membership_subscriptions`: `item_id` (plan), `user_id`, `start_date`, `expiry_date`, `next_billing_date`, `billing_cycle` ENUM(day|week|month|year), trial dates, `billing_amount`, `cancel_sub` ENUM(immediately|expiry), **`status` ENUM(active|canceled|expired|trial|pending)**, `coupon`, `subscription_id` (gateway id).
  - `ur_membership_orders`: `item_id`, `user_id`, `subscription_id` (FK), `created_by`, `transaction_id`, `payment_method`, `total_amount` decimal(26,8), **`status` ENUM(pending|failed|completed|refunded)**, **`order_type` ENUM(free|paid|subscription)**, `trial_status`, `notes`. Indexed on user, creator, type, transaction id.
  - `ur_membership_ordermeta` (order_id, meta_key, meta_value) and `ur_membership_subscription_events` (subscription_id, user_id, `event_type`, `event_status`, title, message, `reference_id`, `meta`).
  - Foreign keys cascade on user/subscription delete.
- **Hazard: schema changes.** Tables are created with `CREATE TABLE IF NOT EXISTS` run through `$wpdb->query()`, not `dbDelta`. That statement never alters an existing table, so adding a column or changing an ENUM needs an explicit migration (see `architecture.md`), and ENUM values in the code must match what the migration wrote.
- **Usermeta** used by the flows: `urm_membership_process` (array with `upgrade`, `renew`, `multiple` keys, via `urm_get_membership_process()`), `urm_pending_role`, `urm_next_subscription_data`, `urm_previous_subscription_data`, `urm_previous_order_data`, `urm_is_user_upgraded`, `urm_is_member_renewing`, `urm_is_payment_retrying` (retry attempt count), `urm_stripe_dispute` / `urm_paypal_dispute` (dispute flags), `urm_last_renewed_on`, `ur_coupon_discount(_type)`, `urm_team_ids`, gateway ids (`ur_stripe_subscription_id`, `urm_paypal_*`), reminder markers (`urm_billing_reminder_sent_for_date`, `urm_expiring_reminder_sent_for_date`).
- **Other feature slugs** checked through `ur_check_module_activation()`: `coupon`, `local-currency`, `membership-groups`, `team`, `payments`, `taxes`, `multiple-registration`, `content-drip`, `custom-email`, `pdf-invoice`, `sms-integration`, `masteriyo-course-integration`, `stripe`, `social-connect`, `frontend-listing`. Test the module-off case.

## Layers
`Controllers` -> `Services` (`MembershipService`, `SubscriptionService`, `OrderService`, `MembersService`, `PaymentService`, `UpgradeMembershipService`, `CouponService`, `EmailService`, gateway services) -> `Repositories` (`MembershipRepository`, `MembersRepository`, `MembersOrderRepository`, `MembersSubscriptionRepository`, `OrdersRepository`, `SubscriptionRepository`...). Put logic in a Service, not in `AJAX.php`.

## Core flow: creating a membership
`MembershipService::create_membership_order_and_subscription()`: `START TRANSACTION`, prepare member data, `defer_role` = true unless the plan or the payment method is `free`, write user meta, create the subscription, create the order, optionally create a team post, `COMMIT`, then fire `ur_membership_subscription_event_triggered` (`trial_started` or `created`). Failure handling here is a `try`/`catch` around the block with a `ROLLBACK`; read it before adding a new failure path.
- **Deferred roles.** A paid plan does not grant its role at registration. The role is stored in usermeta `urm_pending_role` and applied by `MembersService::maybe_grant_pending_role()` only when the member's subscription for that plan is `active` or `trial` (`confirm_payment` and the webhook paths call it). `ur_membership_get_safe_role()` re-checks on read and downgrades a privileged role to `subscriber` unless the plan's author can `promote_users`. Never assign a membership role directly.
- **Payment method validation** is shared by registration, additional purchase and upgrade: `MembershipService::is_valid_payment_method_for_membership()` (free plans accept only an empty or `free` method; `free` on a paid plan is legitimate only for a 100% coupon on a one-time plan). `is_membership_purchasable()` rejects plans hidden from the listing. Use these instead of re-checking inline.
- **Upgrades, renewals and extra purchases** are tracked in `urm_membership_process` and by `SubscriptionService::upgrade_membership()`, `renew_membership()`, `can_upgrade()`, `can_purchase_multiple()`, with cost logic in `UpgradeMembershipService` (paid-to-paid, paid-to-subscription, subscription-to-any).
- Gateways exposed by `PaymentService::build_*`: PayPal, direct bank, Stripe, Mollie, Authorize.net (Mollie and Authorize.net add-on plugins exist alongside), plus `free`.

## Stripe (`Services/Stripe/StripeService.php`, `PaymentGatewaysWebhookActions.php`)
- Settings: options `user_registration_stripe_enabled`, `user_registration_stripe_test_mode`, `user_registration_stripe_<mode>_publishable_key` / `_secret_key`. Keep secret keys server-side.
- Checkout AJAX in `AJAX.php`: `create_stripe_subscription`, `validate_stripe_card_mode`, `confirm_payment` (all reachable logged-out).
- **`confirm_payment` trust chain** (do not weaken any link): nonce `urm_confirm_payment`; a pending order or a matching `urm_membership_process` entry; for logged-out callers `verify_pending_member_session()` (HMAC cookie bound to the member id); then `StripeService::update_order()`. The client-supplied `payment_status` and `paymentIntent.id` are **not trusted**: the server retrieves the PaymentIntent from Stripe with the secret key, requires its `livemode` to match the configured mode and its status to be `succeeded`, finds the order by transaction id, requires the order to belong to the member and to be `stripe`, requires that the intent owns the member's newest order (`TRANSACTION_ORDER_MISMATCH`, the replay fix from 5.2.8), and rejects a duplicate transaction id owned by another order. Only then does it complete the order and call `maybe_grant_pending_role`.
- **Webhooks:** REST `user-registration/stripe-webhook`, `permission_callback` = signature verification via `\Stripe\Webhook::constructEvent`. Events handled by the webhook: `invoice.payment_succeeded`, `invoice.payment_failed`, `payment_intent.payment_failed`, `charge.refunded`, `charge.dispute.created|updated|closed`, `customer.subscription.created`. The hourly missed-event backfill (`run_missed_subscription_backfill`, `run_missed_payment_backfill`, `run_missed_onetime_payment_backfill`, `run_missed_refund_backfill`, `run_missed_dispute_backfill`) separately polls Stripe (`\Stripe\Event::all`) for `customer.subscription.updated|deleted`, `invoice.payment_succeeded|paid`, `payment_intent.succeeded` and `charge.refunded`, so a missed webhook is repaired by polling, not by re-delivery.

## PayPal (`Services/Paypal/`)
- Two generations coexist: `PaypalService.php` (legacy IPN, `?ur-membership-listener=IPN` handled on `init`, verified by posting back to PayPal and checking `VERIFIED`) and `NewPaypalService.php` (REST orders and subscriptions, ~4,700 lines). Legacy PayPal Standard on registration forms is flagged by form meta `user_registration_enable_paypal_standard`; `UR_Install` sets `urm_is_legacy_paypal_user` when old global PayPal settings exist.
- **Webhooks:** REST `user-registration/paypal-webhook`, `permission_callback` = `verify_webhook_signature` (PayPal's verify endpoint). Events handled: `CHECKOUT.ORDER.APPROVED`, `PAYMENT.CAPTURE.COMPLETED`, `PAYMENT.CAPTURE.REFUNDED`, `PAYMENT.SALE.REFUNDED`, `PAYMENT.SALE.COMPLETED`, `CUSTOMER.DISPUTE.CREATED|UPDATED|RESOLVED`, `BILLING.SUBSCRIPTION.CREATED|ACTIVATED|UPDATED|SUSPENDED|CANCELLED|EXPIRED|PAYMENT.FAILED`. Handlers skip already-completed transactions.
- Return/verification tokens use `hash_equals` (`urm_paypal_verification_token`).

## Refunds, disputes and failed renewals
- **Refunds.** `StripeService::handle_refunded_charge()` marks the order `refunded` and cancels the linked subscription only on a **full** refund; a partial refund leaves the subscription unchanged (`apply_refund_to_order_and_subscription()`).
- **Disputes.** Stripe `charge.dispute.created|updated|closed` (`handle_dispute_*`) and PayPal `CUSTOMER.DISPUTE.CREATED|UPDATED|RESOLVED` (in `NewPaypalService.php`, not read in detail), plus `run_missed_dispute_backfill()` for both. A dispute is recorded in usermeta (`urm_stripe_dispute`, `urm_paypal_dispute`), reported to the admin once, and for a real Stripe dispute the membership is revoked; a Stripe inquiry (`warning_*` status) is only flagged and reported. A replayed `created` never overwrites a final outcome, and after a won dispute an admin restores access by hand.
- **Expiry holds while the gateway is still collecting.** `SubscriptionService::daily_membership_expiration_check()` waits `urm_expiry_grace_hours` (filter, default 12) so the backfill can catch a renewal, then asks Stripe about the subscription: `past_due`, `active` or `trialing` hold the expiry (an `active` or `trialing` one is synced to the local row first). A Stripe `invoice.payment_failed` carrying `next_payment_attempt` keeps an `active` member active while Stripe retries. A PayPal subscription marked pending-cancel (usermeta `urm_pending_cancel_<subscription_id>`) is cancelled at PayPal only when its expiry is reached.
- **Plugin-side retries (off by default).** Options `user_registration_payment_retry_enabled`, `user_registration_payment_retry_count` (default 3) and `user_registration_payment_retry_interval` (default 3). `daily_payment_retry_check()` -> `failed_payment_retry_callback()` counts attempts in usermeta `urm_is_payment_retrying` (a counter, not a flag), sends `payment_retry_failed` on each failure and `payment_retry_cancel` after the last, then clears the counter.
- **Admin deletes or cancels a subscription.** `cancel_subscription_by_id( $subscription_id, $send_email, $is_upgrade, $force_cancel )`: `$force_cancel` forces an immediate gateway cancel (PayPal cancel instead of suspend, Stripe now instead of period end). It tries the gateway of the last completed order first, because a pending renewal may not own the stored gateway id.
- **Coupon usage limits.** `ur_claim_coupon_usage()`, `ur_release_coupon_usage()`, `ur_change_coupon_usage( $code, $delta, $enforce_limit )` and `ur_coupon_has_remaining_uses()` in `includes/functions-ur-core.php` update the coupon's stored usage. Do not edit coupon usage meta directly; whether every coupon path already goes through these helpers was not audited.

## Legacy payment fields (frozen)
Form-level payment fields (`single_item`, `multiple_choice`, `subscription_plan`, plus `total_field`, `quantity_field` and a range field with `enable_payment_slider`) are **frozen**: the form builder no longer offers them, and a site takes payments through membership instead. `ur_get_frozen_payment_field_keys()` lists the keys (the filter `user_registration_payments_menu_field_keys` extends the charging ones).
- **Decided once, stored as an option.** `UR_Install::install()` records `urm_is_legacy_payment_fields_user` (1 when any form, published or not, already has a frozen field, via `ur_site_has_any_frozen_payment_field()`) and `urm_is_legacy_ecommerce_addons_user` (1 when the Stripe or payments feature is on or the standalone `user-registration-stripe` plugin is active). `ur_update_529_legacy_payment_fields_flag` in `$db_updates` backfills the first flag for upgraded sites. Do not recompute these from live data later.
- **Per form, not per site.** `ur_legacy_payment_fields_enabled( $form_id )` is true only for a form that already carries a frozen field (`ur_form_has_legacy_payment_fields()`); a new form (`$form_id = 0`) is always frozen, even on a legacy site. Called with no argument it answers for the site. The filter `user_registration_legacy_payment_fields_enabled` can override either. In free, `includes/admin/class-ur-admin-menus.php` uses it to skip the locked payment-fields upsell section in the form builder for a frozen form.
- **Remote form templates** listed by `ur_get_legacy_payment_form_template_slugs()` are stripped from the Add New library for every site (`ur_exclude_legacy_payment_form_templates()`), so a new form cannot pick up a frozen field from a template.
- **Add-on tiles.** `ur_legacy_ecommerce_addons_enabled()` hides the standalone Stripe and PayPal add-on tiles (`includes/RestApi/controllers/version1/class-ur-modules.php`) on sites that were not already using them. Per the comment on that function, Stripe now ships in core (`modules/stripe/`); the old add-on plugin still exists for legacy sites.
- **Payments menu** is registered only when `ur_should_show_payments_menu()` is true (payments feature on, payment records, a membership plan, or a charging form).
- **Site Assistant** shows a notice while a published form still uses a frozen field (`ur_has_forms_with_legacy_payment_fields()`), until the `user_registration_legacy_payment_fields_notice_dismissed` option is set.
- Existing forms keep working: frozen fields are still read, validated and charged on a form that has them. Never remove their handlers, and never treat a missing flag as "frozen" for a site that already charges through them.

## Scheduled work (`includes/class-ur-cron.php` schedules, `Crons.php` runs)
Daily: `urm_daily_membership_renewal_check`, `urm_daily_membership_expiring_soon_check`, `urm_daily_membership_ended_check`, `urm_daily_membership_expiration_check`, `urm_run_delayed_subscription`, `urm_daily_payment_retry_check`. Hourly: `urm_missed_payment_events_check` -> `Crons::membership_missed_payment_check` -> `SubscriptionService::membership_missed_payment_check` -> `urm_backfill_missed_payment_events`, which for Stripe and PayPal runs five polls (adding `run_missed_dispute_backfill`) (`run_missed_subscription_backfill`, `run_missed_payment_backfill`, `run_missed_onetime_payment_backfill`, `run_missed_refund_backfill`) from the last-synced time. A 10-minute transient `urm_backfill_running` stops overlapping runs, each gateway keeps its own sync time (`urm_last_stripe_payment_backfill_sync_time`, `urm_last_paypal_backfill_sync_time`) that advances only when the whole window succeeded, so a failed window is searched again, and the expiry check waits a grace period so the backfill can catch a renewal first. Biweekly: `user_registration_usage_stats_scheduled_events`. Renewal, expiry, retry and backfill bugs live in `SubscriptionService` plus the gateway service, not in checkout code; they run with no user present, so there is no nonce or session to lean on.

## Events and emails
Subscription lifecycle is published through `do_action( 'ur_membership_subscription_event_triggered', $payload )` (fired from `MembershipService`, `SubscriptionService` and `AJAX.php`). **Free has no listener for it and nothing in free writes `ur_membership_subscription_events`; the writer (`SubscriptionEventsService`, `MembersSubscriptionEventsRepository`) exists only in Pro.** Free creates the table and reads it (`Views/subscription-edit.php`). Other hooks: `ur_membership_order_status_failed`, `user_registration_membership_renewal_failed`, filter `user_registration_membership_before_register_member`, `urm_member_registered`. Membership emails go through `Admin/Services/EmailService.php` with templates and settings under `modules/membership/includes/Emails/`, separate from the core email system.

## Gateway logging
`PaymentGatewayLogging` records webhook and transaction events (including raw request data). Do not add keys, tokens or card data to what it logs.

## Invariants to keep when changing anything here
1. Verification (signature, PaymentIntent retrieval) runs before any state change.
2. A replayed, duplicated or out-of-order event changes nothing the second time.
3. Amount, currency, plan and role come from server-side records, never the request.
4. Public (logged-out) endpoints stay bound to the registering session and to a pending order.
5. Free-plan and full-coupon paths cannot be reached by forging a gateway value.
6. Order, subscription and role stay consistent on every failure path (declined, abandoned 3DS, webhook before return URL, return URL before webhook).
