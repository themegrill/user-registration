# Registration, login gating and user state

Read from `includes/functions-ur-core.php` (`ur_process_registration`), `includes/frontend/class-ur-frontend-form-handler.php` (`handle_form`), `includes/class-ur-user-approval.php`, `includes/functions-ur-account.php`. Line numbers drift; search the symbol.

## The registration pipeline
1. **Entry.** The front-end form posts AJAX `user_registration_user_form_submit` (registered for logged-out users) -> `UR_AJAX::user_form_submit()` -> `ur_process_registration( $nonce_value )`. A non-AJAX fallback (`ur_fallback_submit`) goes through `UR_Form_Handler::process_registration()`.
2. **`ur_process_registration`:** capability check for a logged-in submitter (`ur_registration_user_capability`, default `create_users`); captcha verification (v2, invisible v2, v3, hCaptcha, Cloudflare; keys from `user_registration_captcha_setting_*` options, type from form meta `user_registration_form_setting_configured_captcha_type`); `ur_users_can_register()` for logged-out visitors (filterable via `ur_register_setting_override`); decodes the `form_data` JSON (passwords are masked in the log); calls `UR_Frontend_Form_Handler::handle_form()`.
3. **`handle_form` order** (each is a hook other code depends on):
   `user_registration_validate_form_data` (filter by reference; field validators attach here; **every callback must return the array or it is wiped**) -> `user_registration_reorganize_form_data` -> `user_registration_response_array` (validation errors; if non-empty, respond with them and stop) -> role decision -> `user_registration_before_register_user_filter` -> action `user_registration_before_register_user_action` -> `user_registration_before_insert_user` -> Akismet filter `user_registration_get_akismet_validate` -> `wp_insert_user()` -> `user_registration_before_user_meta_update` -> `ur_update_user_meta()` -> action `user_registration_after_user_meta_update` -> login-option branch -> `user_registration_success_params` -> action `user_registration_after_register_user_action` -> `user_registration_success_params_before_send_json` -> `wp_send_json_success`.
4. **`after_register_user_action` is deferred for payments.** It fires immediately only when `success_params['payment_process']` is falsy. For paid membership flows it is stored in usermeta `ur_deferred_after_register_args` and replayed later by `Admin::maybe_fire_deferred_after_register` on `urm_member_registered` (priority 5), once, guarded by `ur_deferred_after_register_fired` (`modules/membership/includes/Admin.php`). The installed add-ons register on this action about 25 times in total, so its timing, arguments and once-only behaviour are a contract.

## Role assignment (security-critical)
The form setting `user_registration_form_setting_default_user_role` is used only if it is a known role. A privileged role (`ur_registration_role_is_privileged()`) is honoured only when the submitter is a logged-in user with `manage_options` or the registration capability; anyone else gets `subscriber`. Then filter `user_registration_user_role` applies. Membership roles are a separate, deferred mechanism (see `membership-payments.md`). Never take a role from request data.

## What gets stored
- WP user row via `wp_insert_user()` (login defaults to the email local part through `check_username()`).
- Field values as usermeta `user_registration_<field_name>` (`UR_Frontend_Form_Handler::ur_update_user_meta`); fields in `ur_get_fields_without_prefix()` are stored unprefixed and WP user-table fields are skipped. Checkbox values are JSON-decoded, files are handled separately.
- Bookkeeping usermeta: `ur_form_id`, `ur_user_ip`, `ur_login_option`, `ur_registered_language`, `ur_requires_payment` (`yes`, set server-side when the login option is `payment` and the form has a visible membership field), `ur_registration_source`.
- For membership registrations, a 2-hour transient `urm_pending_login_<uid>` plus a cookie carrying an HMAC bind the pending payment/auto-login flow to the registering browser.

## Login options and user state
- Options: `auto_login`, `email_confirmation`, `admin_approval`, `admin_approval_after_email_confirmation`, `payment`. `ur_get_user_login_option()` reads usermeta `ur_login_option`, falling back to the form meta `user_registration_form_setting_login_options` and then the global option `user_registration_general_setting_login_options` for users created before the meta existed.
- State usermeta: `ur_user_status` (`UR_Admin_User_Manager::APPROVED = 1`, `PENDING = 0`, `DENIED = -1`), `ur_confirm_email`, `ur_admin_approval_after_email_confirmation`, `ur_disable_users`, and for the payment option `ur_payment_status`, `ur_payment_method`, `ur_requires_payment`.
- **The login gate** is `UR_User_Approval::check_status_on_login` on the core filter `wp_authenticate_user`. It returns a `WP_Error` with code `disable_user`, `pending_approval`, `denied_access`, `user_email_not_verified` (message carries a nonce-protected resend link) or `user_payment_pending` (for PayPal/Mollie it embeds a payment link built by `PaymentService::build_response`). For membership users the last order's status replaces the payment meta. Hooks: `ur_user_before_check_status_on_login`, `ur_user_before_check_email_status_on_login`, `ur_user_before_check_payment_status_on_login`, filter `user_registration_user_disabled_message`.
- Other login-time hooks: `wp_login` -> `track_first_login`; membership `Frontend::reconcile_membership_role`.
- Care with types: some status checks mix strings and ints (`'0' === $status['user_status']` next to `(int)` comparisons on `DENIED`).

## Read before changing this area
- **Nonce handling on registration submit.** `ur_process_registration()` receives `$nonce_value` from `UR_AJAX::user_form_submit()` and `UR_Form_Handler::process_registration()`. Before changing this path, read how (and where) that value is verified rather than assuming a check exists, and remember an AJAX action `get_recent_nonce` exists, which suggests full-page caching shaped the design.
- The registration success message and redirect logic branch on POST fields (`ur_stripe_payment_method`, `is_membership_active`, `membership_type`) and on legacy form meta `user_registration_enable_paypal_standard`. These are client-supplied hints; anything that grants access must be re-derived server-side.

## Other front-end handlers
`UR_Form_Handler` (`includes/class-ur-form-handler.php`): `process_login`, `process_lost_password`, `process_reset_password`, `save_profile_details`, `save_change_password`, `export_confirmation_request`, `ur_force_logout_all_devices`. AJAX `update_profile_details` checks a nonce and, for other users, capability. Email-confirmation and approval tokens use `hash_equals` (`class-ur-email-approval.php`, `class-ur-email-confirmation.php`).
