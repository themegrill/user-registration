# Ecosystem: free, Pro and the add-ons

This checkout is only the free plugin. Two other kinds of code run on top of it or a copy of it. Facts below were read from `user-registration-pro` and 38 `user-registration-*` add-on folders installed next to this checkout on one developer machine; other machines may not have them, so treat the lists as evidence, not a registry.

## The three pieces
| Piece | What it is | Repo (from `git remote`) |
|---|---|---|
| **Free** (this repo) | `user-registration`, "User Registration & Membership", version 5.x | this repo |
| **Pro** | A **complete standalone plugin, not an add-on.** `user-registration-pro`, version 6.x, same text domain `user-registration`. It declares its own `UserRegistration` class and `UR()` function, defines `UR_PRO_ACTIVE` as `true`, and contains a synced copy of free's `includes/`, `modules/`, `src/`, `templates/`, `assets/` plus Pro-only code (for example `modules/file-downloads`). | `themegrill/user-registration-pro` |
| **Add-ons** | About 38 separate plugins, each its own repo, slug, text domain, version and Composer `vendor/`, for example `user-registration-advanced-fields`, `-conditional-logic`, `-two-factor-authentication`, `-stripe`, `-mailchimp`, `-social-connect`, `-multi-part`, `-woocommerce`, `-zapier`. | `themegrill/user-registration-<name>` |

## How they relate at runtime
- **Free and Pro are alternatives, not layers.** Pro's bootstrap guards `UR()` with `function_exists`, and activating Pro deactivates free (`user_registration_free_deactivate()` in Pro's `user-registration.php`). So free code runs in two places: as the free plugin, and as the synced copy inside Pro.
- **Pro is a strict superset of free, by file path.** Measured on this machine (Pro 6.2.8 vs free 5.2.8): `includes/` 277 shared files and 155 Pro-only; `modules/` 116 shared and 48 Pro-only; `templates/` 31 and 15; `src/` 226 and 88; `assets/` 631 and 199; **zero free-only tracked files** in any of them (counts are `git ls-files` on each repo's `develop`). Pro-only code lives in `includes/pro/` (`addons/` 58 files, `form/`, `admin/`, `External/`, `form-analytics/`, `blocks/`, `Analytics/`, `country-and-state/`), in `modules/file-downloads/` (35 files), and as extra files **inside shared modules** (7 in `content-restriction`, 5 in `membership`, 1 in `content-drip`), plus a few in `includes/admin/settings`, `includes/admin/notifications` and `RestApi/`. Of the 393 shared files (all types) in `includes/` and `modules/` (measured earlier from working trees, when Pro was on a fix branch), 12 differed in content, all under `modules/membership` payment code, consistent with in-flight branches rather than a deliberate fork.
- **Free fires hooks that only Pro implements.** Example: `ur_membership_subscription_event_triggered` is fired throughout free's membership code, and the table `ur_membership_subscription_events` is created and read by free, but the code that writes it (`SubscriptionEventsService`, `MembersSubscriptionEventsRepository`) exists only in Pro. **A hook, function, option or table with no caller or listener in free is not dead code.** Never delete or "clean up" one on that basis; check Pro and the add-ons first, or leave it and say so.
- **The sync is one-way and wholesale** (`.github/sync-file-list.yml`, target branch `release/develop`). Your change to a synced file reaches Pro's copy of that file. Free-only behaviour must therefore be conditioned on `UR_PRO_ACTIVE` (see `includes/functions-ur-core.php`; `UR_Install` also keeps a separate migration list for Pro-active sites), and code written for Pro-only features must not break when it runs as free.
- **Some former add-ons were merged into the core.** Pro's activation code lists `user-registration-payments`, `-content-restriction`, `-frontend-listing` and `-membership` as merged add-ons (Pro 5.0+). Their features now live in `modules/`. Do not assume a feature is an add-on because it once was.
- **Add-ons depend on the core, and most on Pro.** 33 of the 38 installed add-ons reference `user-registration-pro/user-registration.php` in their main file or top-level `includes/*.php`; a sample (`advanced-fields`, `functions-uraf-core.php`) refuses to run unless Pro is active and at a minimum version, and shows an admin notice otherwise. They are not loaded by free; they attach to it through hooks and helper functions.
- **Tier and upsell logic lives in free too:** `ur_get_license_plan()`, upsell settings sections, and admin-menu checks for Pro (`class-ur-admin-menus.php`, `class-ur-admin-settings.php`, `settings/class-ur-settings-license.php`).
- **The Add-ons screen is data-driven:** `includes/admin/class-ur-admin-addons.php` reads bundled JSON (`assets/extensions-json/`), filterable through `user_registration_addons_sections` and `user_registration_addons_section_data`.
- `ur_addon_updater()` (add-on updates through the licence) is defined in both free's and Pro's `includes/functions-ur-core.php`; an edit to one copy must keep the other's behaviour in mind.

## What the add-ons actually consume (a floor, not the full list)
Counted across the installed add-ons' own code, excluding `vendor/` and `node_modules/`.

- **Hooks they attach to** (among the most used): `user_registration_after_register_user_action`, `user_registration_settings_hide_save_button`, `user_registration_form_settings_save`, `user_registration_after_form_settings_save`, `user_registration_after_form_settings`, `user_registration_my_account_enqueue_scripts`, `user_registration_enqueue_scripts`, `user_registration_integrations_classes`, `user_registration_get_settings_pages`, `user_registration_account_menu_items`, `user_registration_field_options_general_settings`, `user_registration_registered_form_fields`, `user_registration_one_time_draggable_form_fields`, `user_registration_field_keys`, `user_registration_form_settings_integration`, `user_registration_email_classes`, `user_registration_sanitize_field`, `ur_user_approved`, plus the dynamic `user_registration_settings_*`, `..._get_settings_*`, `..._get_sections_*` families and the style-customizer and email-template section hooks.
- **Helpers they call** (among the most used): `ur_get_single_post_meta`, `ur_string_to_bool`, `ur_clean`, `ur_get_logger`, `ur_sanitize_dimension_unit`, `ur_get_form_id_by_userid`, `ur_addon_updater`, `ur_get_valid_form_data_format`, `ur_get_user_login_option`, `ur_get_post_content`, `ur_get_all_user_registration_form`, `ur_deprecated_function`, `ur_string_translation`. They also read `UR()->version` and use `UR()->form->get_form()`.
- Consequences: the form-settings, settings-page, field-registration and registration-lifecycle hooks are the most heavily depended-on surface. A signature, priority, argument or return-shape change there breaks add-ons you cannot see.

## How to check the blast radius
1. In the free repo, grep every caller (`Grep`), as usual.
2. If the developer has Pro and add-ons checked out next to this plugin (`wp-content/plugins/user-registration-*`), search them read-only: start Claude with `claude --add-dir ../user-registration-pro` (repeat for the add-ons that matter). Do not commit machine-specific paths into `.claude/settings.json`.
3. If they are not available, say explicitly in the report that add-on and Pro consumers were **not** checked, and list the hooks, helpers or data you changed so a maintainer can check.
4. Never edit Pro or add-on repos from a task scoped to this one; flag the needed follow-up.
